# ایمیل، پایش و استقرار

## ایمیل OTP
`OTP_EMAIL_FROM` یک آدرس ایمیل ساده روی دامنهٔ تأییدشدهٔ Resend است. در production یا با تنظیم `RESEND_API_KEY`، مقدار خالی، نامعتبر یا دامنهٔ نمونه مانع راه‌اندازی می‌شود. تأیید دامنه در Resend همچنان لازم است. خطای سرویس ارسال به فراخواننده برمی‌گردد؛ متن خام پاسخ سرویس در لاگ قرار نمی‌گیرد.

## نشست و Origin
درخواست POST به `/auth/refresh` و `/auth/logout` باید هدر `Origin` برابر مبدأ `CLIENT_URL` داشته باشد. مقدار غایب، `null` یا زیردامنهٔ دیگر رد می‌شود و کوکی/نشست تغییر نمی‌کند. مرورگر این هدر را می‌فرستد؛ کلاینت‌های خط فرمان نیز باید آن را صریح تنظیم کنند. CORS و SameSite همچنان فعال‌اند.

## پایش
- `SENTRY_DSN` اختیاری است. بدون آن هیچ رویدادی به Sentry ارسال نمی‌شود. با آن خطاهای ثبت‌شده در logger گزارش می‌شوند؛ متن خطا، اطلاعات درخواست، کاربر، breadcrumbs و دادهٔ اضافی حذف می‌شوند و محل stack برای عیب‌یابی باقی می‌ماند. این اتصال tracing یا session replay ندارد.
- با `METRICS_TOKEN` تصادفی حداقل ۳۲ کاراکتری، `/metrics` برای Prometheus فعال می‌شود. scraper باید `Authorization: Bearer ...` بفرستد. بدون تنظیم توکن پاسخ 404 است؛ توکن نادرست 403 می‌گیرد.
- متریک‌ها تعداد/مدت درخواست و وضعیت process را دارند؛ مسیرهای حاوی شناسه، ایمیل و IP برچسب متریک نیستند. هشدار نرخ 5xx و شکست health را در سرویس پایش خود تعریف کنید.

## Staging
Workflow «Deploy staging» دستی و فقط روی main اجرا می‌شود. CI همان commit باید موفق باشد. تصویر با SHA کامل منتشر می‌شود؛ سپس migration و راه‌اندازی روی میزبان Linux اجرا می‌شوند. در شکست health، کانتینر قبلی برمی‌گردد؛ migration معکوس نمی‌شود، بنابراین تغییر schema باید با نسخهٔ قبلی سازگار باشد.

پیش‌نیازهای محیط GitHub با نام `staging`:

- Variables: `STAGING_HOST` و `STAGING_USER`.
- Secrets: `STAGING_SSH_KEY` و `STAGING_KNOWN_HOSTS` با کلید میزبانِ از قبل تأییدشده.
- روی میزبان: Docker، Bash و flock؛ دسترسی خواندن تصویر GHCR برای کاربر deploy؛ فایل `/opt/online-exam/server.env` با دسترسی محدود و تنظیمات واقعی، و PostgreSQL/Redis/MinIO آماده.
- شبکهٔ host مخصوص Linux است؛ پورت برنامه باید پشت reverse proxy با TLS و firewall باشد. محیط staging از دیتابیس و کلیدهای production جدا باشد. از دیتابیس پیش از migration پشتیبان بگیرید.

این workflow بدون تنظیم مقصد و secrets اجرا نمی‌شود. Codespace مقصد دائمی staging نیست. فعال‌سازی Sentry و اجرای واقعی deploy به تنظیمات حساب شما نیاز دارد؛ هیچ مقصد یا کلید فرضی در مخزن قرار نگرفته است.

## Migration و تست
تاریخچهٔ اجراشده تغییر نمی‌کند. CI نصب تازه و تطابق مدل را بررسی می‌کند. baseline تنها در یک برنامهٔ جداگانه با نسخه‌بندی و تطبیق دیتابیس‌های موجود انجام می‌شود؛ حذف پوشهٔ recovery یا تغییر نام migrationهای اجراشده راه‌حل نیست.

`npm test -w server` همهٔ فایل‌های `*.test.ts/cjs/mjs/js` زیر tests را خودکار پیدا می‌کند؛ helperها اجرا نمی‌شوند. تست‌های قدیمی CJS برای حفظ mockها باقی مانده‌اند و تست‌های جدید می‌توانند TS باشند. lint و format:check در CI اجباری‌اند. برای قالب‌بندی سرور: `npm run format -w server`.

تست‌های مرورگر پرداخت از درگاه شبیه‌سازی‌شده استفاده می‌کنند؛ تراکنش واقعی sandbox نیازمند تنظیمات درگاه و بررسی جداگانه است. تست‌های یکپارچهٔ پرداخت سرور، تغییر وضعیت و جلوگیری از تسویهٔ تکراری را پوشش می‌دهند.

## استقرار تولیدی

برای Compose و Nginx تولیدی، S3 مدیریت‌شده، بک‌آپ رمزگذاری‌شده و timerهای هشدار، [راهنمای تولید](PRODUCTION.fa.md) را ببینید. این تنظیمات بدون اجرای مراحل میزبان فعال نمی‌شوند.
