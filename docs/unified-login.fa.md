# ورود یا ثبت‌نام یکپارچه

این تغییر بر پایهٔ commit `4ee93ef` آماده شده است و migration ندارد.

- صفحهٔ نخست یک شناسه می‌گیرد: «شماره تماس یا پست الکترونیکی».
- شناسهٔ تأییدشده: شماره به کد پیامکی، ایمیل به رمز عبور می‌رود. روش جایگزین قبلی حفظ شده است.
- شناسهٔ جدید یا ثبت‌نام تأییدنشده به ثبت‌نام می‌رود؛ شناسه دوباره تایپ نمی‌شود. تأیید مالکیت، نقش و سیاست تأیید مدرس همچنان در سرور اعمال می‌شوند.
- برگشت بالای کارت، مرحلهٔ قبلی را باز می‌کند؛ برگشت از بازیابی رمز به فرم رمز همان شناسه است.
- بازیابی برای ایمیل/شمارهٔ ثبت‌شدهٔ حساب است، نه افزودن شمارهٔ جدید به یک حساب ایمیلی.
- برچسب شناور با فوکوس یا مقدار بالا می‌رود؛ حالت تاریک و موبایل پشتیبانی می‌شوند.
- POST /auth/entry فقط شناسهٔ نرمال‌شده و مرحلهٔ بعدی را می‌دهد؛ اطلاعات پروفایل یا نشست نمی‌دهد. تشخیص مسیر ثبت‌نام عمداً وضعیت ثبت شناسه را قابل استنباط می‌کند. درخواست‌ها محدود می‌شوند و پاسخ cache نمی‌شود. خرابی دیتابیس/Redis نباید به ثبت‌نام هدایت کند.

## تست در Codespace

از ریشهٔ پروژه:

```bash
npm test -w client
node --test server/tests/googleAuth.test.cjs server/tests/authErrors.test.cjs server/tests/sessionAccess.test.cjs
npm run build -w server && npm run build -w client && npm run lint -w client
```

سرور را پس از اعمال تغییرات دوباره اجرا کنید تا `/auth/entry` فعال شود. PostgreSQL و Redis باید روشن باشند.

تست عملی با حساب آزمایشی:

1. شمارهٔ ثبت‌شده → کد SMS؛ ویرایش و بازگشت نباید خودبه‌خود کد تکراری بفرستند.
2. ایمیل ثبت‌شده → رمز؛ فراموشی رمز → شناسهٔ بازیابی → کد → رمز جدید. برگشت از رمز جدید نیازمند کد جدید است، چون کد قبلی مصرف شده.
3. شناسهٔ جدید → انتخاب نقش → اطلاعات → تأیید → کد؛ پیش از تأیید کد نباید وارد حساب شود.
4. برگشت تک‌تک مراحل، حفظ شناسه و پاک‌شدن رمز/کد ورود را بررسی کنید.
5. فیلد خالی، شناسهٔ نامعتبر، کد اشتباه و قطع سرویس باید پیام قابل‌فهم بدهند.
6. نمایش موبایل و حالت روشن/تاریک، ورود گوگل برای حساب قبلی و ثبت‌نام گوگل را بررسی کنید.

تست مرورگر محلی با پاسخ‌های شبیه‌سازی‌شده انجام شده؛ تحویل واقعی پیامک/ایمیل و Google OAuth به تنظیمات محیط شما وابسته است.
